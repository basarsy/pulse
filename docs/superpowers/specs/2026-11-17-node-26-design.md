# Node 26

## Why

Node.js 20 reached end-of-life in April 2026, and Pulse still uses it in two places: the dashboard
CI job runs `npm ci`, lint, tests and the build on Node 20, and the dashboard image builds on
`node:20-alpine`. The README lists this under "Next".

CI shows a second, quieter problem. On `main`, the backend job warns:

> Node.js 20 is deprecated. The following actions target Node.js 20 but are being forced to run on
> Node.js 24: actions/checkout@v4, actions/setup-java@v4, actions/upload-artifact@v4.

and `setup-java v4 is deprecated and will no longer receive updates`; the other jobs name
`actions/setup-node@v4` and `helm/kind-action@v1.10.0` the same way. The actions themselves are on
a runtime GitHub is retiring, and `helm/kind-action@v1.10.0` is from April 2024.

## Goals

- The dashboard builds, lints and tests on Node 26, the current Active LTS line, in CI and in its
  image.
- Every action in `ci.yml` is on a major that runs on Node 24, so CI shows no deprecation warnings.
- The README says Node 26 and no longer lists this as "Next".

## Non-goals

- Upgrading the dashboard's own dependencies (Vite 5, Vitest 1). A Vite upgrade is a separate
  change; this one only proves the current toolchain works on Node 26.
- The nginx base image and the backend's base images.

## Approaches

From the Node.js release schedule (`nodejs/Release/schedule.json`):

| Line | Status on 2026-11-17 | End of life |
|---|---|---|
| 22 | Maintenance | 2027-04-30 |
| 24 | Maintenance since 2026-10-20 | 2028-04-30 |
| 26 | **Active LTS since 2026-10-28** | 2029-04-30 |

- **Node 26:** **chosen.** It's the Active LTS line, so it gets the longest support window, and a
  reviewer sees a current runtime rather than one already in maintenance.
- *Node 24:* rejected. It left Active LTS a month ago.
- *Node 22:* rejected. It ends in April 2027, so this change would come back within months.

The GitHub Actions *runtime* (`runs.using`) is separate from the Node the dashboard runs on. For the
actions, take each one's latest major (all `runs.using: node24`), checked against their release
notes:

| Action | From | To | Notes |
|---|---|---|---|
| `actions/checkout` | v4 | v7 | No input changes. |
| `actions/setup-java` | v4 | v6 | No input changes; Maven caching works as before. |
| `actions/upload-artifact` | v4 | v7 | v7 adds an opt-in `archive: false`; default still zips. |
| `actions/setup-node` | v4 | v7 | v5's automatic caching only applies without `cache:`; we set it explicitly. |
| `helm/kind-action` | v1.10.0 | v1.15.2 | Pin kind to v0.33.0, the action's default, so kind and its kubectl (v1.37) match. |

kind 0.33 still uses kindnet, which enforces NetworkPolicies, so the network-policy test keeps
proving what it proves today.

## Found while verifying: `localStorage` in tests

On Node 26, all 7 API-client tests failed with `Cannot read properties of undefined (reading
'clear')`. Since Node 25, Node defines its own `localStorage` global, which is `undefined` unless
`--localstorage-file` is given. Vitest 1's jsdom environment only replaces a global Node already
has if the key is on its own list (`populateGlobal` in `vitest/dist/vendor/index.*.js`), and
`localStorage` isn't, so the tests saw Node's instead of jsdom's. The token store
(`src/api/tokens.ts`) uses `localStorage`, so this hits app code under test, not just test code.

- **Pass `--no-experimental-webstorage` to Vitest's workers** (`test.poolOptions` in
  `vite.config.ts`), only when the running Node knows the flag
  (`process.allowedNodeEnvironmentFlags`, true on Node 22.4+), so local runs on older Node still
  work: **chosen.** It's a few lines and fixes it for every test file at once.
- *Upgrade Vitest:* rejected here. Newer majors need a newer Vite, which is the separate change
  named in the non-goals.
- *Stub `localStorage` per test:* rejected. Each new test file would have to remember it.

`vite.config.ts` now uses `process`, so `@types/node` (26, matching the runtime) is a dev
dependency and `tsconfig.node.json` names it. Vite's own type definitions, which the test files
load through `vitest`, reference Node's types, so the app's tsconfig sees them too; the app
type-checks and builds the same.

## Verification

- In a `node:26-alpine` container: `npm ci`, `npm run lint`, `npm test`, `npm run build` in
  `pulse-dashboard`.
- The dashboard image builds from `node:26-alpine`.
- On the PR, every CI job passes and no job has a Node 20 or action-deprecation annotation. (The
  notice that `ubuntu-latest` is moving to Ubuntu 26 is unrelated and stays.)
